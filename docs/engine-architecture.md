# SystemSim simulation engine

How a run works, what each component models, and every simplifying
assumption. The numbers the UI shows come only from what's described here.

Code: `packages/engine/src/sim/` (pure TypeScript, no UI or DOM).
Runs in the browser in a Web Worker (`frontend/src/worker/simulation.worker.js`).

## Decisions

| Decision | Choice |
|---|---|
| Where it runs | Browser Web Worker. No server; the engine package can move server-side later unchanged. |
| Call model | **Blocking.** An app server holds a thread while it waits on downstream calls. |
| Time model | As fast as possible; progress streamed after each ~20 ms slice. |
| MVP scope | All 10 components with core behaviors (deferred features listed at the end). |

## Pipeline

```
editor graph + { durationSec, seed }
   │
   ▼
compile.ts      validate (at least one client, editor connection rules, no loops, required
                downstream links), clamp every setting to its field range
   │
   ▼
Simulator       discrete-event loop: events are closures in a min-heap ordered by
                (time, insertion order); the clock jumps from event to event
   │   stations.ts  component models built from resources.ts (ServerPool, TokenBucket)
   │   metrics.ts   per-second windows + a latency histogram
   ▼
result.ts       final numbers (same fields as the simulation_results table)
bottleneck.ts   which component limits throughput, and why
```

**Determinism.** A seeded PRNG (mulberry32) plus insertion-ordered ties mean the
same graph, duration and seed always give an identical result. Slicing a run
for the worker never changes the result (this is tested).

## Units

| Quantity | Unit |
|---|---|
| Simulated time | seconds (float). Settings in ms are divided by 1000 when used. |
| Rates | per second |
| Latency in results | milliseconds |
| Utilization | 0–1: busy time ÷ (capacity × elapsed), time-weighted (exact, not sampled) |

## Requests

- **Arrivals** follow a Poisson process at the Client's rate (exponential gaps).
  Patterns:
  - *constant*
  - *burst*: 3× the rate for the last 10 s of every 30 s cycle
  - *ramp*: rises linearly from 10% to 100% over the first half, then stays flat

  Variable rates are generated by thinning a peak-rate Poisson process.
- Each request is a **read** or a **write** (the Client's read share).
- With several downstream targets, a Client splits traffic round-robin.
- **Deadline:** clients give up after **30 s**. An API Gateway can shorten this
  to its `timeoutMs`, which becomes an end-to-end deadline for everything
  behind it.
- **Outcomes:**
  - **success**
  - **rejected:** refused by a full queue, a rate limit or a connection limit
  - **timed out:** the deadline passed first
  - **failed** is reserved for failure injection (not yet modeled)
- **Throughput** counts successes completed *during* the traffic period only.
  Backlog cleared during drain doesn't count as capacity.
- **Latency percentiles cover successful requests only.** A rejection answers
  instantly; counting it would make an overloaded system look fast.
- **Timed-out work:** work already in progress keeps running (wasted effort,
  as in real systems). Work still *queued* for a timed-out request is dropped
  when its turn comes, or earlier as soon as it reaches the front of the line.
  That way dead waiters don't use queue capacity meant for live requests.
  An app server doesn't start new downstream calls for a timed-out request.
- **Drain:** traffic stops at `durationSec`. The run continues until nothing is
  in flight, or at most 30 s more, which is enough to settle every deadline.

## Component models

Settings in `code font` are the editor fields.

| Component | Model |
|---|---|
| **Client** | The traffic source (see Requests). |
| **API Gateway** | Token bucket at `rateLimitRps` (burst = 1 s worth); over the limit → rejected. Constant `latencyMs`. Sets the deadline from `timeoutMs`. Round-robin forwarding. |
| **Load Balancer** | At most `maxConnections` requests in flight through it; more → rejected. Constant `latencyMs`. `strategy`: round-robin, least-connections (fewest in flight) or random. |
| **App Server** | Two resources. **Threads** = `instances × maxConcurrency`, FIFO queue of `queueCapacity` (full → rejected). **Cores** = `instances × cpuCores`. A request takes a thread, waits for a core, computes for an exponential time with mean `serviceTimeMs`, releases the core, then **still holding the thread** calls each downstream in order (stopping at the first failure), then releases the thread. Instances are pooled, as if perfectly balanced internally. |
| **Cache** | Token bucket at `maxOpsPerSec`. Constant `latencyMs`. A read hits with probability `hitRatePct` and returns. Misses and all writes (write-through) go downstream. With no downstream, a miss completes at the cache. `memoryMb` doesn't affect the hit rate yet: the hit rate is given, not simulated from keys. |
| **CDN** | Like a cache without a throughput limit. Constant `edgeLatencyMs`. `bandwidthMbps` is deferred. |
| **Relational DB** | The primary plus `readReplicas`, each with a pool of `connectionPool` connections and an unbounded wait (bounded only by deadlines). Writes → primary only; reads → round-robin over all nodes. Service time is exponential: mean `readLatencyMs` / `writeLatencyMs`. Replication lag isn't modeled. |
| **NoSQL DB** | `maxOpsPerSec` split evenly over `partitions` (each a token bucket; keys spread uniformly). Over a partition's limit → rejected. Exponential read/write latency. No concurrency cap beyond throughput. |
| **Message Queue** | **The caller is answered after `latencyMs` once the message is stored.** `consumers` workers process messages FIFO by calling downstream. Backlog over `maxDepth` → rejected. Background work never counts toward user latency or request totals. It's reported as processed/failed/backlog on the queue. |
| **Object Storage** | Token bucket at `maxRps`; exponential `latencyMs`. `bandwidthMbps` is deferred. |

Stations with only a throughput limit (Cache, NoSQL, Object Storage) are
modeled as **rate-limited delays with unlimited concurrency**. Their
"utilization" is accepted throughput ÷ capacity.

## Bottleneck analysis

- **Saturated:** utilization ≥ 95%, or ≥ 2% of its calls rejected (a few random
  rejections, e.g. a hot partition, don't count). **Strained:** ≥ 80%.
- When several components are saturated, the **deepest** one (furthest from
  the client) is reported, and the others are listed as "also saturated".
  Upstream saturation is usually a policy limit (a rate limit) or
  back-pressure from below: blocked threads waiting on the deeper component.
  The deepest saturated component caps successful throughput.
- **App servers:**
  - **CPU-bound:** cores are about as busy as threads. Capacity ≈ cores ÷
    mean service time.
  - **Thread-starved:** threads are full but the CPU isn't. They're waiting on
    downstream calls, and the explanation names which ones.
- **Databases:** when upstream app threads are stuck waiting on a saturated DB,
  the explanation calls out the cascade.
- Totals for the analysis are captured **when traffic stops**, so drain time
  doesn't dilute utilization.

## Safety limits (spec §11)

| Limit | Value | When exceeded |
|---|---|---|
| Duration | 1–3,600 s | rejected by validation |
| Events processed | 50,000,000 | run stops with an explanation |
| Requests in flight | 200,000 | run stops ("far past saturation") |
| Chart points kept in a result | 300 (downsampled: p95/p99 keep the worst value, p50 is weighted by successes) | — |

Client timeouts are kept in a FIFO line rather than the event heap. Every
request has the same 30 s timeout, so they arrive in order, and finished
requests cost nothing.

Runs happen in a worker in ~20 ms slices, so **Stop** takes effect within one
slice and the UI never freezes. Throughput is roughly 1 million events per second.

## Validation of the model

Tests (`packages/engine/src/sim/*.test.ts`) check the simulator against queueing theory:
- **M/M/1** mean response time 1/(μ−λ): measured 20.26 ms vs 20 ms in theory
- **M/M/c** (Erlang C) mean response time, within 10%
- **Little's law** L = λW, within 5%

Plus behavioral tests for every component, determinism by seed, and
slicing-equals-one-shot.

## Deferred (not modeled yet)

- Payload sizes, network bandwidth, memory pressure
- Component failures and recovery (`failedRequests` is always 0)
- Autoscaling policies
- Rich request types (image/video/file) and per-type costs
- Changing traffic intensity during a run
- Cache hit rate emerging from memory size and key distribution
- Replication lag, partition hot spots
